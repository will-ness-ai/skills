Chapter 1 · where you are, and what broke

Why does a finished test file still cost 40–55MB?

Vitest gives every test file a fresh sandbox. It should throw the sandbox away when the file ends. But why does the memory stay?

Look at these two words first.

A worker is a process that lives for a long time. It starts one time and runs many test files in order. It keeps heavy data between files, like resolved paths, file contents, and compiled code.

A sandbox is where one test file runs. Node calls this a vm context. It has its own global variables and its own fake browser (jsdom). Vitest makes a new sandbox for every file. When the file ends, the sandbox should become garbage.

Vitest calls this setup a vm pool. This only works well if each finished sandbox is actually collected.

That did not happen. In a real suite of 638 files, each worker held 40–55MB for every finished test file. The worker spent about 30% of its CPU collecting garbage. It filled up and restarted 19 times per run. This threw away the caches that the pool is meant to keep. A full run took 487 seconds.

The rule for this bug is simple: if anything outside the sandbox still points at the sandbox, the whole sandbox stays alive. Six different things pointed at it. Any one of those things was enough to keep it alive. This is why this change has six fixes instead of one.

After all six fixes, the run takes 235 seconds.

The six things that pointed at it

How you prove a leak like this is gone

You cannot see this by looking. So, this change includes a test. The test fails if the leak comes back.

Ten test files are added. They are all exactly the same. Each file imports a big array, does a dynamic import, registers a fixture, and writes to the page. These actions create the types of state that the six causes hold onto.

There is also a custom test environment. It lives in the worker, not in a sandbox. Every time Vitest asks it for a new sandbox, it does two things: it forces garbage collection, then it counts how many old sandboxes are still alive.

test/e2e/fixtures/leak-probe/leak-probe-env.ts9–11, 25, 38
v8.setFlagsFromString('--expose-gc')const gc = vm.runInNewContext('gc')v8.setFlagsFromString('--no-expose-gc')  if (alive <= 4) {  await assertReleased()
  1. Node does not have a way to force garbage collection. To do this, the test turns a flag on, takes a function out of a temporary sandbox, and turns the flag off on the next line. The rest of the run is normal.
  2. The limit is four, not zero. It must be four. Node keeps the newest one or two sandboxes until a new file replaces them. Four catches leaks that grow with every file, but it ignores the small constant number at the end.
  3. The count happens at the start of the next file, not when a file ends. This is the only time the previous sandbox is truly finished and the next one does not exist yet.

Before this change, nine of the ten sandboxes were still alive. The limit is four, so the test fails. If you remove any one of the six fixes, the test fails again.

Chapter 2 · one missing line

Who still holds the file's code after the test ends?

The sandbox should be deleted when the file ends. But an object outside the sandbox is still pointing to it.

The cause is an unlikely object. It is the tool that makes error messages easy to read.

When a test fails, you want the stack trace to show your original source file. It should not show the transformed code that Vitest ran. Vite does this by replacing Error.prepareStackTrace one time for the whole process. To map errors back to the source, it keeps a list of all compiled code it has seen.

That list stays in the worker. The list is never emptied unless you call a function. Vite provides a way to empty it using close(), but Vitest never called it.

Chapter 3 · a flag, not a value

How can one property flag keep a whole sandbox alive?

Three global variables were made without configurable: true. Why does a missing flag cause a memory leak instead of just being a style choice?

Chapter 6 explains why the sandbox object itself often cannot be freed. Because of this, Vitest must empty it. It deletes everything the test file added. This leaves a small empty shell instead of a large full one.

Emptying it means calling delete on every global. You cannot use delete to remove a property if it was made without configurable: true. The command does not throw an error. It just returns false and does nothing.

The expect library adds three globals the first time it runs inside a sandbox. In a vm pool, it runs inside the test file's sandbox. This means those globals belong to that file. All three are getters. Each getter holds onto every matcher and comparison function used in that file.

packages/expect/src/state.ts14–28

  1. The value did not change. Only the flag changed. This is the full fix for two of these three globals.
  2. The middle global already had the flag before this change. No comment, commit, or review explains why. The other two did not have it. That difference is the bug.
  3. This is a getter, not a stored value. It holds onto the file's matchers, comparison functions, and expect state. You must delete the property to release that closure.
packages/vitest/src/runtime/runVmTests.ts36–41
Object.defineProperty(globalThis, '__vitest_index__', {  value: VitestIndex,configurable: true,writable: true,})
  1. A fourth global has the same problem in a different package. This one points to the whole public Vitest API.

The flag pins the sandbox, not the value. By default, Object.defineProperty gives you configurable: false. Usually, this just means "internal, do not change." Inside a sandbox you want to throw away, it means something stronger: the sandbox can never be released.

Chapter 4 · two leaks of the same shape

What happens when a listener outlives the thing that registered it?

Two lists in the worker grew by one entry for every test file. Why did that keep the whole sandbox alive? Why did the second list cause problems even though its listener had no work to do?

Both causes here are subscriptions. Something in the worker keeps a callback. That callback belongs to one test file, but nothing ever removes it. The two causes need opposite fixes. This contrast is important.

The subscription nobody cancelled

Vitest lets a test run react when you press Ctrl-C. Each test file added a callback for that event. That callback captured the file's test runner. Through the runner, it also captured the file's code and its sandbox.

The list of callbacks lives in the worker. It had no way to remove anything. After 638 files, the list held 638 callbacks.

  1. This is a regular array at the top of a module in the worker. Subscribing added items to it, but nothing ever removed them. The fix is these four lines: onCancel now returns a function. That function removes the entry again.

  1. Calling it inside finally means a test file still unsubscribes even if it throws an error. The non-vm code path received the same fix in runBaseTests.ts:93.

The hook that did nothing, and cost everything

The second cause is more unusual. It is the reason for this chapter.

Vitest lets a fixture live for the whole worker instead of just one file. To clean those up, you need a hook. This hook is registered once per test runner. But in a vm pool, worker-wide fixtures become per-file fixtures. In this mode, the hook has nothing to clean up.

Even so, it still cost one sandbox per file. The test runner loads inside the file's sandbox. Therefore, the function it provides belongs to that sandbox. But the list holding that function belongs to the worker. A hook that did no work held everything in memory.

You cannot fix this by unsubscribing. You must fix it by never subscribing.

  1. The hook is now only created in modes where it has work to do. In a vm pool, the property is simply set to undefined.
  2. This unchanged line makes that safe. The call was already optional. Leaving the property as undefined is allowed. The old code just always filled it in.

Changing what onCancel returns changes its signature. There is a second implementation of it. The browser client has its own copy and leaks nothing because the browser never uses sandboxes. This change was made so both versions still match the same type. If you add a third runtime later, it must also return an unsubscribe function.

Chapter 5 · the cause that is not in the diff

Why must a dynamic-import callback capture nothing?

Two arrow functions held onto the object that handles the current file. Why does Node refuse to release them? Why did fixing this make the test suite twice as fast?

You cannot find this cause by looking at the code changes. It is inside Node.

When you compile code with vm, you can give Node a callback. Node runs this callback later when that code calls a dynamic import(). Node must keep your callback until then. Node keeps it as long as the compiled code exists. Node also keeps everything the callback captured. The Node code says this is on purpose.

This design is usually fine. It becomes a memory leak when your callback captures a file's state and the compiled code lives longer than that file. Both things happened here.

node · internal/modules/esm/utils.js183–184inside Node
// To prevent it from being GC'ed.registry.callbackReferrer ??= referrer;
  1. Node does this on purpose. No line in the Vitest diff shows this behavior. But you need to know this to understand the rest of this chapter.

The fix is to make both callbacks module-level functions that capture nothing. These functions must find the correct file handler when they are called. The two module systems need different methods to do this.

importModuleDynamically: this.executor.importModuleDynamically,initializeImportMeta: (meta) => { meta.resolve = this.resolve }
packages/vitest/src/runtime/vm/esm-executor.ts16–17
const vmContext = (mod.context as any)?.[VITEST_VM_CONTEXT_SYMBOL]return vmContext?.executor
packages/vitest/src/runtime/vm/utils.ts57–58, 73–75
let activeVmExecutor: ExternalModulesExecutor | undefinedexport function setActiveVmExecutor(e) { activeVmExecutor = e }export async function activeImportModuleDynamically(spec, ref) {return activeVmExecutor?.importModuleDynamically(spec, ref)}
  1. For ES modules: Ask the module which sandbox it belongs to. Get the handler from that sandbox. Vitest marks every sandbox with a symbol so you can do this. The callback captures nothing, so it holds no memory.
  2. For CommonJS: You cannot use the same trick because a compiled CommonJS script cannot ask which sandbox it belongs to. Instead, the worker keeps one variable that tracks the current file. The callback reads this variable when it is called. This is safe because a vm pool runs only one file at a time. workers/vm.ts clears this variable when it finishes.

This next part was not the main goal. Now, a compiled CommonJS script does not remember which file created it. This means many files can reuse the same compiled script. The change adds a cache for these scripts.

packages/vitest/src/runtime/vm/commonjs-executor.ts24, 118–119
const cjsScriptCache = new Map<string, vm.Script>()let script = cjsScriptCache.get(filename)if (!script) { script = new vm.Script(code, opts); cjsScriptCache.set(filename, script) }
  1. The cache only works because of the change mentioned above. If the script still remembered its original file, sharing it would cause bugs.

The memory fix and the speed fix are the same thing. Capturing one file's state made the script impossible to release and impossible to share. Removing the capture fixed both problems. Total import time dropped from 1547 seconds to 587 seconds. If a cache cannot be shared, check what it captured. That is usually what is causing the memory leak.

Chapter 6 · when you cannot fix it, contain it

What do you do about a leak in code you do not own?

Two of the six causes are not caused by Vitest code. One is a cache in the JavaScript engine. The other is Node refusing to release a sandbox. What can we do?

Vitest could delete four of the six causes. For these last two, there are different answers: turn one off, and give up on the other.

The engine cache. V8 keeps compiled code in a cache for the whole worker. A cached entry holds the compiled module and its state. Vitest cannot clear this cache. Only memory pressure clears it. This usually happens after the worker is already full. So Vitest turns the cache off. It loses little because Vitest has its own caches that do the same thing.

The sandbox that will not die. Node does not release a sandbox after several scripts run inside it. Internal wrappers keep it reachable even after a full garbage collection. Nothing Vitest does can change this.

If you cannot free the shell, empty it. Delete every global variable the test file added. Clear the fake browser's page too. What leaks now is an empty object instead of a full one.

packages/vitest/src/runtime/workers/vm.ts89–90, 198–200
const initialContextKeys = captureContextKeys(context)  provideWorkerState(context, state)// the engine caches compiled code until memory pressure clears it,// which in practice means after the worker has already filled upv8.setFlagsFromString('--no-compilation-cache')
packages/vitest/src/runtime/vm/utils.ts103–113
export function stripDisposedContext(g, initialKeys) {try { g.document.body.textContent = '' } catch {}for (const key of Object.getOwnPropertyNames(g)) {  if (initialKeys.has(key)) continue  try { delete g[key] } catch {}}}
  1. One line turns off the engine cache for this process. See the warning below. It affects more than it looks like.
  2. Read the line under this one to see why the order matters. Globals are recorded before Vitest installs its own. So Vitest's globals count as “added” and get deleted too. Only the untouched ones stay.
  3. The rule for emptying is: keep what was there when the sandbox started, and delete what anyone added later. The untouched globals must stay because work in progress still needs Promise and setTimeout to exist.
  4. You cannot delete the fake browser's page because document was there at the start. So you blank it instead. In a suite using a fake browser, this is usually the biggest thing being held.

--no-compilation-cache is a V8 flag. V8 flags apply to the whole process. With vmForks, each worker is its own process. So only that worker changes. With vmThreads, workers share the main process. This also turns off the cache for the main thread. The author saw no slowdown and says it might be a permanent setting. It does not have a setting yet.
