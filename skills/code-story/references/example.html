Chapter 1 · where you are, and what broke

Why does a finished test file still cost 40–55MB?

Vitest gives every test file a fresh sandbox and throws it away when the file ends. So why does the memory never come back?

Start with the two words this whole change turns on.

A worker is a long-lived process. It starts once and runs many test files, one after another. It keeps the expensive things between files: resolved paths, file contents, compiled code.

A sandbox is what one test file runs inside. Node calls it a vm context. It has its own global variables and its own fake browser (jsdom). Vitest builds a new one for every file. When the file ends, the sandbox should become garbage.

Vitest calls this arrangement a vm pool. It only pays off if each finished sandbox is actually collected.

It was not. On a real 638-file suite, each worker held 40–55MB for every test file it had finished. It spent about 30% of its CPU collecting garbage, filled up, and restarted 19 times per run — throwing away the caches the pool exists to keep. A full run took 487 seconds.

The rule behind all of it is short: if anything outside the sandbox still points at the sandbox, the whole sandbox stays. Six separate things pointed at it. Any one of them was enough on its own. That is why this change is six fixes and not one.

After all six, the run takes 235 seconds.

The six things that pointed at it

How you prove a leak like this is gone

You cannot eyeball this. So the change ships a test that fails when the leak comes back.

Ten test files are added. They are byte-identical on purpose. Each one imports a big array, does a dynamic import, registers a fixture, and writes into the page — one of each kind of state the six causes hold on to.

Beside them sits a custom test environment. It lives in the worker, not in any sandbox. Each time Vitest asks it for a new sandbox, it first forces garbage collection, then counts how many earlier sandboxes are still alive.

test/e2e/fixtures/leak-probe/leak-probe-env.ts9–11, 25, 38
v8.setFlagsFromString('--expose-gc')const gc = vm.runInNewContext('gc')v8.setFlagsFromString('--no-expose-gc')  if (alive <= 4) {  await assertReleased()
  1. Node gives you no way to force garbage collection. So the test turns the flag on, takes the function out of a throwaway sandbox, and turns the flag off again on the next line. The rest of the run is unaffected.
  2. The limit is four, not zero — and it has to be. Node holds on to the newest sandbox or two until a later file replaces it. Four catches leaks that grow with every file while ignoring that small constant tail.
  3. The count happens at the start of the next file, not when a file ends. That is the only moment when the previous sandbox is truly finished and the next one does not exist yet.

Before this change, nine of the ten sandboxes were still alive at the end. The limit is four, so the test fails. Remove any one of the six fixes and it fails again.

Chapter 2 · one missing line

Who still holds the file's code after the test ends?

The sandbox is discarded when the file ends. So which object outside it is still pointing back in?

The answer is the least likely object in the system: the thing that makes error messages readable.

When a test fails, you want the stack trace to point at your source file, not at the transformed code Vitest actually ran. Vite does this by replacing Error.prepareStackTrace once, for the whole process. To map any frame back to a source, it keeps a list of every file's compiled code that it has ever seen.

That list lives in the worker. It is never emptied unless you ask. Vite gives you the way to ask — close() — and Vitest never called it.

Chapter 3 · a flag, not a value

How can one property flag keep a whole sandbox alive?

Three global variables were created without configurable: true. Why is a missing flag a memory leak and not a style preference?

Chapter 6 explains why the sandbox object itself often cannot be freed at all. Given that, the best Vitest can do is empty it: delete everything the test file added, and let a small empty shell leak instead of a large full one.

Emptying it means calling delete on each global. And delete cannot remove a property that was created without configurable: true. It does not throw. It returns false and does nothing.

The expect library installs three globals the first time it runs inside a sandbox. In a vm pool it runs inside the test file's sandbox, so those globals belong to that file. All three are getters, and each getter closes over every matcher and comparison function registered for that file.

  1. Nothing about the value changed. Only the flag did. That is the entire fix for two of these three globals.
  2. The middle one already had the flag before this change. No comment, commit, or review says why. Its two neighbours did not — and that inconsistency is the bug.
  3. This is a getter, not a stored value. It closes over the file's matchers, comparison functions and expect state. Deleting the property is the only way to release that closure.
packages/vitest/src/runtime/runVmTests.ts36–41

  1. A fourth global with the same problem, in a different package. This one points at the whole public Vitest API.

The flag, not the value, is what pins the sandbox. configurable: false is what Object.defineProperty gives you by default, and it usually just means “internal, leave it alone”. Inside a sandbox you intend to throw away, it means something much stronger: this can never be released.

Chapter 4 · two leaks of the same shape

What happens when a listener outlives the thing that registered it?

Two lists in the worker grew by one entry per test file. Why did that hold the whole sandbox — and why did the second one do it even though its listener had no work to do?

Both causes here are subscriptions. Something in the worker keeps a callback, the callback belongs to one test file, and nothing ever removes it. But they need opposite fixes, and that contrast is the useful part.

The subscription nobody cancelled

Vitest lets a run react to you pressing Ctrl-C. Each test file subscribed a callback for that. The callback captured the file's test runner — and through it, the file's code and its sandbox.

The list of callbacks lives in the worker, and had no way to remove anything. After 638 files it held 638 callbacks.

The hook that did nothing, and cost everything

The second one is stranger, and it is the reason this chapter exists.

Vitest lets a fixture live for the whole worker instead of one file. Tearing those down needs a hook, registered once per test runner. But in a vm pool, worker-wide fixtures are quietly downgraded to per-file fixtures. So in this mode the hook has nothing to tear down.

It still cost a sandbox per file. The test runner is loaded inside the file's sandbox, so the function it hands over belongs to that sandbox — and the list holding it belongs to the worker. A hook that did no work held everything.

You cannot fix that by unsubscribing. You fix it by never subscribing.

  2. This unchanged line is what makes that safe. The call was already optional, so leaving the property undefined is a supported state — the old code just happened to always fill it in.

Changing what onCancel returns is a signature change, and there is a second implementation of it. The browser client has its own copy and leaks nothing — the browser never uses sandboxes. It changed only so both versions still satisfy the same type. Add a third runtime later and it must return an unsubscribe function too.

Chapter 5 · the cause that is not in the diff

Why must a dynamic-import callback capture nothing?

Two callbacks were arrow functions that captured the object handling the current file. Why can Node never release them — and why did fixing that also make the suite twice as fast?

This is the one cause you cannot find by reading the diff. It lives in Node.

When you compile code with vm, you can pass a callback that Node will run later, whenever that code does a dynamic import(). Node has to keep your callback somewhere until then. It keeps it for as long as the compiled code exists, and — deliberately, with a comment saying so — it also keeps whatever your callback was given.

That is a reasonable design. It turns into a leak the moment your callback is a closure over one file's state and the compiled code outlives the file. Both were true here.

node · internal/modules/esm/utils.js183–184not in this diff — it is inside Node
// To prevent it from being GC'ed.registry.callbackReferrer ??= referrer;
  1. Node is holding this on purpose, and says so. Nothing in the Vitest diff shows you this line — but without it the rest of the chapter makes no sense.

The fix is to make both callbacks module-level functions that capture nothing. They then have to find the right file's handler at call time instead, and the two module systems need different tricks for that.

  1. For ES modules: ask the module which sandbox it belongs to, and get the handler from there. Vitest tags every sandbox it creates with a symbol for exactly this. The callback captures nothing, so it holds nothing.
  2. For CommonJS: that trick is unavailable — a compiled CommonJS script has no sandbox to ask. So the worker keeps one variable saying which file is running right now, and the callback reads it at call time. This is safe because a vm pool runs exactly one file at a time. workers/vm.ts clears it at teardown.

Now the part nobody was aiming for. Once a compiled CommonJS script no longer remembers which file compiled it, the same compiled script can be reused by every later file. So the change adds a cache for them.

  1. This cache is only correct because of the change above it. While the compiled script remembered one file, sharing it between files would have been a bug.

The memory fix and the speed fix are the same fix. Capturing one file's state made the compiled script both impossible to release and impossible to share. Remove the capture and you get both. Total time spent importing modules fell from 1547 seconds to 587. When a cache cannot be shared, ask what it captured — that is usually also what is leaking.

Chapter 6 · when you cannot fix it, contain it

What do you do about a leak in code you do not own?

Two of the six causes are not Vitest's code. One is the JavaScript engine's own cache. The other is Node refusing to release a sandbox at all. What is left to do?

Four of the six causes were references Vitest could delete. These two are not, and each gets a different answer: turn one off, and give up on the other.

The engine cache. V8 keeps compiled code in a cache shared by the whole worker. A cached entry holds the compiled module, and through it the file's state. Vitest cannot clear this cache. Only memory pressure clears it — which in practice means the worker has already filled up. So Vitest turns the cache off. It loses little, because Vitest keeps caches of its own that cover the same ground.

The sandbox that will not die. Node does not release a sandbox once several scripts have run inside it. The internal wrappers keep it reachable even after a forced full collection. Nothing Vitest does will change that.

So if the shell cannot be freed, empty it. Delete every global the test file added, and blank the fake browser's page. What leaks afterwards is an empty object instead of a full one.

packages/vitest/src/runtime/workers/vm.ts89–90, 198–200
+ const initialContextKeys = captureContextKeys(context)  provideWorkerState(context, state)+ // the engine caches compiled code until memory pressure clears it,+ // which in practice means after the worker has already filled up+ v8.setFlagsFromString('--no-compilation-cache')

+ export function stripDisposedContext(g, initialKeys) {+   try { g.document.body.textContent = '' } catch {}+   for (const key of Object.getOwnPropertyNames(g)) {+     if (initialKeys.has(key)) continue+     try { delete g[key] } catch {}+   }+ }
  1. One line turns the engine cache off for this process. See the warning below — it reaches further than it looks.
  2. Read the line under this one to see why the order matters. The globals are recorded before Vitest installs its own, so Vitest's globals count as “added” and get deleted too. Only the untouched ones survive.
  3. The single rule of emptying: keep what was there when the sandbox was built, delete what anyone added afterwards. The untouched globals have to stay — work already queued still needs Promise and setTimeout to exist while it finishes.
  4. The fake browser's page cannot be deleted, because document was there from the start. So it is blanked instead. In a suite using a fake browser this is usually the single biggest thing being held.

--no-compilation-cache is a V8 flag, and V8 flags apply to the whole process. With vmForks each worker is its own process, so only that worker is affected. With vmThreads the workers share the main process, so this also turns the cache off for the main thread. The author measured no slowdown from it and notes it may deserve a setting. It does not have one yet.

Everything else in this change

Nine files carry the six fixes. Here is every other file, so you know nothing was hidden from you.

  • runBaseTests.ts (+40 / −35) — the size is misleading. Three lines actually changed. The other 72 are the same loop, shifted two spaces because it moved inside a try. There is nothing to find in them. runVmTests.ts (+41 / −31) has the same trap.
  • leak-probe/a.test.js … j.test.js (10 files) — identical to each other. Ten exist so a per-file leak has ten chances to climb above the limit of four. Read one and skip nine.
  • leak-probe/module-state.js (+1) — a 10,000-element array, big enough to be obvious in a heap snapshot. That is its entire job.
  • types/worker.ts (+1 / −1) — says onCancel now returns a function. This one line is what forces every caller in chapter 4 to be updated.
  • browser/src/client/client.ts (+7 / −1) — the browser's own onCancel, changed to match the type. It fixes no leak.
  • external-executor.ts (+2 / −1) — one call site, updated for chapter 5.
  • test/e2e/test/vm-threads.test.ts (+28 / −1) — runs the leak test through the real CLI. The in-process test harness holds references of its own, which would drown the signal.

Where the “why” in this story came from

  • The pull request description — every number here: 40–55MB per file, 30% of CPU, 19 restarts, 487s → 235s, and 1547s → 587s importing.
  • The author's own review notes — the process-wide flag warning, and the browser signature change.
  • Outside this repo — Vite's stack-trace list, Node's callback registry, V8's cache flag. Chapters 2, 5 and 6 depend on these, and none appear in the diff. Each is marked where it is used.
